# 信号の周期の当てはめ（段階 0）

交差点ごとに、信号の周期と位相（いつ青になるか）が実測データから求められるかを、手元で確かめるスクリプトです。計算は [信号の周期の推定](../../docs/timing-estimation.md) の「暦」と「当てはめ」と同じです。サーバーの cron とアプリに時刻表を出す前の検証に使います。

- Python 3.10 以降が必要です。標準ライブラリだけで動きます。
- 何も送信せず、ファイルを読むだけです。

## 入力

次の 2 種類のファイルを、いくつでも混ぜて渡せます。形式は自動で見分けます。

| 入力 | 作り方 |
| --- | --- |
| アプリの記録ファイル（`.jsonl`） | 「受信データを記録する」で作ります。[現地確認の手順](../../docs/field-test.md) をご覧ください。 |
| サーバーの `reports` 表の書き出し（`.json`） | 運用者が D1 から書き出します（下の例）。 |

記録ファイルは、アプリと同じ規則で信号の変化に直します（Type 2 の信号パケットだけを読み、受信が 5 秒を超えて途切れたら状態を忘れます）。時計は合っているものとして扱い、受信時刻 `t`（ミリ秒まで）をそのまま使います。記録ファイル 1 つを 1 回分の報告として数えます。

`reports` の書き出しは、行のリスト、`{"results": [...]}`、`[{"results": [...]}]`（wrangler の `--json` の出力）のどれでも読めます。`payload` は JSON の文字列でも、オブジェクトでも構いません。`clock_ok = 1` の行だけを使い、`received_day` が `--today`（初期値は今日の UTC の日付）以降の行は、サーバーと同じく使いません。

```sh
# 例：運用者が reports 表から必要な列だけを書き出す
npx wrangler d1 execute <データベース名> --remote --json \
  --command "SELECT id, intersection_id, received_day, clock_ok, payload FROM reports WHERE clock_ok = 1" \
  > reports.json
```

## 使い方

```sh
# 2 日分の記録を比べる（段階 0）
python3 Tools/timing/fit_plans.py --min-days 2 --by-day a-0910.jsonl b-0911.jsonl

# サーバーの書き出しを、公開と同じ条件で調べる
python3 Tools/timing/fit_plans.py reports.json

# 機械で読める形で出す
python3 Tools/timing/fit_plans.py --json reports.json > fit.json
```

| オプション | 内容 |
| --- | --- |
| `--min-days N` | 青の始まりのある日数の下限（初期値 7） |
| `--min-reports N` | 報告の行数の下限（初期値 2）。記録ファイルでは別のファイルの数 |
| `--by-day` | セルごとに、日ごとの位相を表示する。2 日を並べて比べるときに使う |
| `--json` | JSON で出力する |
| `--today YYYY-MM-DD` | `reports` の行は、この日（UTC）より前に受信したものだけを使う |
| `--intersection ID` | その交差点だけを表示する |

公開の条件は、サーバーと同じ日数 7 日・報告 2 行です。記録がまだ少ないときは、`--min-days 2` などで日ごとの位相がそろっているかを先に試せます。

## 出力の見かた

セル（交差点 × 信号の番号 × 日の種類 × 30 分の時間帯）ごとに 1 行です。

| 列 | 中身 |
| --- | --- |
| `intersection`、`slot`、`day`、`bin` | 交差点 ID、信号の番号（1〜6）、日の種類（平日・土・日）、日本時間の時間帯 |
| `C(s)` | 周期（秒）。青の始まりの `cycle` の中央値 |
| `±1s` | `cycle` のうち C から ±1 秒以内のものの割合。8 割未満だと周期が変わる信号 |
| `R_ev` | 採用した基準での `R_events`（青の始まりの時刻がどれだけそろっているか。1 に近いほどそろっている） |
| `epoch R_d/spread` | 基準が Unix 時刻の起点のときの、日ごとの位相の `R_days` とばらつき |
| `midnight R_d/spread` | 基準が日本時間の 0 時のときの、同じ値 |
| `ref` | ばらつきをミリ秒に四捨五入して、小さいほうの基準（等しければ `epoch`） |
| `phase(s)` | 位相（基準から青が始まるまでの秒数。C 秒で一周） |
| `days`、`reports` | 青の始まりのある日数、使った報告（記録）の数 |
| `green/blink(s)` | 青と青点滅の長さの中央値（秒） |
| `verdict` | `OK` は公開の条件を満たす。`NG` のあとに理由 |

`--by-day` では、各セルの下に日ごとの位相（両方の基準）と、採用した基準での全体の位相との差を表示します。同じ時間帯の日ごとの位相が 1〜2 秒以内にそろっていれば、その交差点は定周期で、信号機の時計が合っていると考えられます。日によって何十秒もずれるときは、周期が変わる信号か、時計の合わない信号機です。

### 結果の意味

- `OK`：その時間帯の次の青の始まりを、およそ ±（ばらつきの 2 倍 + 2 秒）の幅で推定できます。
- `NG` の理由：
  - 周期のデータが 3 件未満：途切れずに 2 周期以上受信できていません。受信を続けて記録し直します。
  - 周期が定まらない：交通量に応じて周期が変わる信号か、押しボタン・感応式の信号です。推定は出せません。
  - 日数・報告が不足：別の日に、同じ時間帯でもう一度記録します。
  - `R_events` が低い、ばらつきが大きい：日によって青になる時刻がそろっていません。推定は出せません。

## テスト

```sh
python3 -m unittest discover -s Tools/timing -v
```

合成した信号のデータで、定周期の当てはめ、日数が 7 日に足りないときの不合格、周期が変わる信号の不合格、祝日の除外、日付の 0 時を基準にした信号、基準の選び方（ばらつきをミリ秒に四捨五入して比べる）、パケットの読み取りを確かめます。

## 仕様との対応で決めたこと

仕様に書かれていない細部は、次のとおりにしています。

- 青と点滅の長さの中央値は、個数が偶数のとき小さいほうです（周期 C と同じ）。
- 祝日表の範囲（2026〜2027 年）の外の日は、サーバーと同じく対象外にします（祝日かどうかが分からないため）。それより前の記録を調べるときは、祝日表を足してください。
- サーバーは、最後の日が当てはめの日（UTC）の 21 日前より前のセルを保存しません（時刻表の保存期間）。このスクリプトは古い記録も調べられるように、この条件を使いません。
- 記録ファイルの行は、ファイルに書かれた順に読みます。時刻が戻った行は、受信が途切れたものとして扱います。
