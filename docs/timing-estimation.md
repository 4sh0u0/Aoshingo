# 信号の周期の推定（時刻表）

この文書は、実測データから交差点ごとの信号の周期と位相（いつ青になるか）を求め、その交差点を誰も通っていないときにも「次の青の始まり」をおおまかに推定する仕組みの取り決めです。アプリ（`Packages/AoshingoKit/Sources/FieldDataKit/Timing/`、`App/Timing/`）、サーバー（`server/src/timing.ts`）、オフラインの検証スクリプト（`Tools/timing/`）はすべてこれに従います。変えるときは、コードと同じ Pull Request でこの文書も更新してください。

通信の形式は [送信 API の仕様](field-data-api.md)（schema 4 と `GET /v1/plans`）にもあります。

## 安全の原則

- **推定は横断の判断に使えません。** アプリは推定した色を読み上げず、青や赤の色で表示せず、振動もしません。示すのは「次の青の始まりはおよそ何秒後か」の幅だけです。
- 信号を Bluetooth で受信しているときは、推定を出しません。受信した実際の信号だけを示します。
- 交差点から 80 m 未満にいるときは、受信できていなくても推定を出しません（このときこそ推定に頼ってしまうため）。
- 推定が成り立つのは、同じ時間帯なら毎日同じ時刻に青になる交差点（定周期で、信号機の時計が合っている交差点）だけです。交通管制センターが交通量に応じて周期を変える交差点、感応式や押しボタン式の信号は、当てはめの条件を満たさないので推定を出しません。
- 受信した実際の信号と推定が 5 秒より大きくずれたら、その時間帯の推定はその日のうちは出しません。

## 段階 0：オフラインでの検証

時刻表をアプリに出す前に、交差点ごとに推定が成り立つかを `Tools/timing/` のスクリプトで確かめます。入力は、アプリの「受信データを記録する」で作った記録ファイル（JSON Lines）か、サーバーの `reports` 表から書き出した JSON です。スクリプトは下の「当てはめ」と同じ計算をして、セルごとの周期、位相のばらつき、公開の条件を満たすかを表示します。手順は [実地テストの手順](field-test.md) と `Tools/timing/README.md` にあります。

## 送るデータ（schema 4）

schema 4 は schema 3 に次を加えたものです。

| フィールド | 中身 |
| --- | --- |
| `sentAt` | アプリが `POST /v1/reports` の要求を作る直前の端末の時刻（Unix ミリ秒、整数）。schema 4 では必須です。送り直すたびに付け直します。 |
| `transitions[].ms`、`steps[].ms` | 変化した時刻のミリ秒の部分を 100 ミリ秒単位に切り下げた値（0〜900、100 の倍数）、または `null`。`t`（秒）と合わせて 0.1 秒単位の時刻になります。 |

### 端末の時計の確認

- サーバーは、要求を受け付け始めた時刻（本文を読む前）と `sentAt` の差が 2000 ミリ秒以内なら、その報告の行に `clock_ok = 1`、それより大きければ `clock_ok = 0` を保存します。schema 3 以前の行は `NULL` です。
- 差そのものと `sentAt` は保存しません（端末ごとに決まったずれは、報告どうしを結び付ける手がかりになるため）。
- 当てはめには `clock_ok = 1` の行だけを使います。時刻を補正することはしません。

## 暦：日の種類と時間帯

- 日付と時刻は日本時間（UTC+9）で決めます。
- **日の種類**：`0` = 平日（月〜金）、`1` = 土曜、`2` = 日曜。
- **対象外の日**：国民の祝日・休日（[内閣府「国民の祝日について」の CSV](https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv)）、12 月 29 日〜1 月 3 日、収録している祝日表の範囲（現在は 2026〜2027 年）の外の日。対象外の日のデータは当てはめに使わず、アプリも対象外の日には推定を出しません。祝日表は毎年 2 月ごろに内閣府が翌年分を公表するので、そのときにアプリとサーバーの両方を更新します。
- **時間帯**（`bin`）：日本時間の 0 時からの分を 30 で割って切り捨てた値（0〜47）。

### 収録している祝日・休日

## 当てはめ

サーバーの cron とオフラインのスクリプトは同じ計算をします。

### 使うデータ

- `clock_ok = 1` で、受信日（UTC）が当てはめを行う日（UTC）より前の行。受け取った当日のデータは使いません（時刻表が更新された時刻から、協力者がいつ通ったかが分からないようにするため）。
- 変化の時刻 `T`（ミリ秒）= `t × 1000 + ms − gap ÷ 2`。`ms` が `null` なら 500、`gap` が `null` なら 0 とします。日の種類と時間帯は `T` で決めます。
- **青の始まり**：`from = Red` かつ `to = Green` の transition。
- **青の長さ**：`from = Green` の transition の `held`。**点滅の長さ**：`from = BlinkGreen` の transition の `held`。

### セル

当てはめは「交差点 × 信号の番号（slot）× 日の種類 × 時間帯」のセルごとに行います。

1. **周期 C**：セルの青の始まりの `cycle`（`null` を除く）を秒に四捨五入します。3 件以上必要です。C はその中央値（個数が偶数のときは小さいほう）です。C から ±1 秒以内のものが 8 割以上でなければ、周期が変わる信号として公開しません。C は 30〜300 秒でなければなりません。C が決まらないセルは、ここで公開しないと決まります。以下 `Cms = C × 1000` です。
2. **位相**：青の始まり `T_k` ごとに、2 つの基準で角度を求めます。
   - `epoch`：基準 = 0（Unix 時刻の起点）
   - `midnight`：基準 = `T_k` の日（日本時間）の 0 時
   - 角度 `θ_k = 2π × ((T_k − 基準) mod Cms) ÷ Cms`
3. 日本時間の日付ごとに角度を平均（単位ベクトルの平均の向き）して、その日の位相 `ψ_d` とします。
   - `R_days = |平均_d e^{iψ_d}|`、`R_events = |平均_k e^{iθ_k}|`
   - ばらつき `spread = Cms ÷ 2π × √(−2 ln R_days)`（`R_days = 1` なら 0）
   - 2 つの基準のうち、ミリ秒に四捨五入した `spread` が小さいほうを採ります（等しければ `epoch`）。周期が 1 日を割り切るときは、2 つの基準の `spread` は計算の誤差を除いて等しくなるので、その誤差では決めません。
   - 位相 `phase` = `平均_d e^{iψ_d}` の向きを 0〜2π にとり、`Cms × 向き ÷ 2π` を四捨五入して `Cms` で割った余り（ミリ秒）。
4. **公開の条件**（すべて満たすこと）：青の始まりのある日付が 7 日以上、そのデータを含む報告の行が 2 行以上、`R_events ≥ 0.9`、`spread ≤ 3000` ミリ秒。満たさないセルは保存せず、前回の結果があれば消します。日数と報告の行数は、この判定にだけ使い、保存も配信もしません。
   - 日数を 7 日にしているのは、日ごとの位相がばらつく（推定に向かない）交差点が、少ない日数でたまたま条件を満たして公開されないようにするためです。周期 120 秒、日ごとの位相の標準偏差が 8 秒の交差点（1 日に青の始まり 1 回）を模擬すると、3 日では約 19%、7 日では約 1.4% の確率で `spread ≤ 3000` になります。
5. **青と点滅の長さ**：セルの `held` の中央値（ミリ秒、個数が偶数のときは小さいほう）。データがなければ `null`。
6. **最後の日**：青の始まりのある最後の日付（日本時間、`YYYY-MM-DD`）。サーバーの中で古くなった時刻表を消すためだけに使い（「保存期間」）、配信しません。

## サーバーでの保存と配信

- `timing_plans` 表：公開の条件を満たしたセルごとに 1 行。交差点 ID、slot、日の種類、時間帯、`cycle`（ミリ秒）、`reference`（`epoch` か `midnight`）、`phase`、`spread`、`green`、`blink`（ミリ秒）、最後の日（日本時間）、更新した日（UTC）。日数と報告の行数は持ちません。当てはめのたびに交差点ごとに置き換えます。
- `timing_places` 表：交差点ごとに、保存中の observation のうち最後に受信した名称（メッセージ種別 0）と位置（種別 1）の `raw`。信号機が発信している公開の情報です。最後に当てはめた日（UTC）も持ち、当てはめの順番を決めるのに使います。
- `timing_snapshot` 表：`GET /v1/plans` で返す時刻表の写し（下の「配信用の写し」）。
- 最後の日と更新した日は配信しません。協力者が 1 人だけの交差点では、時間帯（30 分）と交差点の位置に日付が加わると、その人がどの日の何時ごろにそこを通ったかが分かり、毎日見比べれば日ごとに追えてしまうためです。日数と報告の行数を保存も配信もしないのも、同じ理由です。

### 保存期間

- 時刻表の cron は、毎回はじめに、最後の日が実行した日（UTC）の 21 日前より前の行を `timing_plans` から削除します。当てはめでも、最後の日がそれより前のセルは保存しません。
- 時刻表が 1 つもなく、21 日前の日（UTC）以降に受信した `clock_ok = 1` の行もない交差点は、`timing_places` からも削除します。
- アプリは時刻表を、作られた日から 7 日まで使います。セルの推定が出るのは、そのセルの最後の日から長くて 28 日ほどです。

### 当てはめの cron

- 毎日 18:30 UTC（03:30 JST）に動きます。
- 対象は、21 日前の日（UTC）から前の日までに受信した `clock_ok = 1` の行があり、その日にまだ当てはめていない交差点です。前回の当てはめの後に受信した行のある交差点（まだ当てはめていない交差点を含む）を先に、その中ではまだ当てはめていない交差点、前回の当てはめが古い交差点の順に処理します。新しい行のない交差点は、その後に前回の当てはめが古い順に当てはめ直します。1 回に最大 12 交差点です。
- 期限切れの削除（最大 4,000 行）と当てはめで書き込む時刻表の行（削除と追加）が、合わせて 4,000 行を超えたら、新しい交差点を始めず、残りは翌日に回します。`timing_places` の削除は 1 回 100 行までです。

### 配信用の写し

- cron は最後に（当てはめや削除の一部が失敗した回も）、`GET /v1/plans` の応答の `intersections` の中身を SQL で組み立て直し、`timing_snapshot` 表に置き換えます。交差点の順に、約 1 MB ごとの行に分けます（D1 の 1 つの値は 2 MB までのため）。時刻表が 1 つもなければ、中身が空の行を 1 行だけ置きます。
- 各行には、作った日（cron を実行した日、UTC）を `generated` として持ちます。
- `GET /v1/plans` はこの表だけを読みます（1 回の要求で読む行数は分けた行の数）。cron と cron の間に `timing_plans` が変わっても、次の cron まで応答は変わりません。

### `GET /v1/plans`

`Authorization: Bearer <token>`（`/v1/reports` と同じ送信用トークン）が必要です。本文はありません。

- 送信用トークンを持つアプリ（実測データの提供に協力している利用者）にだけ時刻表を返します。
- クエリは付けません。アプリは、どの交差点に関心があるかをサーバーに知らせないため、常にすべての交差点の時刻表を取得します。クエリが付いていれば（`?` のあとに何か書かれていれば）`400 bad_request` です。
- レート制限は `/v1/reports` と同じ制限器を、トークン ID に `plans:` を付けたキーで使います。
- 応答には `Cache-Control: private, max-age=3600` を付けます。
- 応答は、最後に動いた時刻表の cron が作った写しです。時刻表が 1 つ以上ある交差点だけを返します（`id` の昇順、`plans` は `slot`、`dayType`、`bin` の昇順）。

`200`：

```json
{
  "generated": "2026-11-11",
  "intersections": [
    {
      "id": "1234ABCD",
      "name": "CE01000000...",
      "position": "CE01000001...",
      "plans": [
        {
          "slot": 1, "dayType": 0, "bin": 14,
          "cycle": 120000, "reference": "epoch", "phase": 37400, "spread": 1800,
          "green": 24000, "blink": 6000
        }
      ]
    }
  ]
}
```

| フィールド | 中身 |
| --- | --- |
| `generated` | 写しを作った cron を実行した日（UTC、`YYYY-MM-DD`）。最初の cron の前は `null` で、`intersections` は空です。 |
| `name`、`position` | `timing_places` の名称（種別 0）と位置（種別 1）の `raw`（`CE01` で始まる大文字の 16 進）。なければ `null`。アプリは `PICSParser` で読みます。 |
| `slot` | 1〜6 |
| `dayType` | 0（平日）、1（土曜）、2（日曜） |
| `bin` | 0〜47（日本時間の 30 分ごとの時間帯） |
| `cycle` | 周期（ミリ秒、1000 の倍数） |
| `reference` | `epoch` または `midnight` |
| `phase` | 基準からの青の始まりの位相（ミリ秒、0 以上 `cycle` 未満） |
| `spread` | 日ごとの位相のばらつき（ミリ秒） |
| `green`、`blink` | 青と青点滅の長さの中央値（ミリ秒）、または `null` |

`plans` の要素は、この 9 つのフィールドだけです。日数、報告の行数、最後の日、更新した日は返しません。

エラー：`400 bad_request`、`401 invalid_token`、`429 rate_limited`

## アプリでの表示

### 推定のしかた

1. 今の日付が対象外の日なら、推定しません。
2. 今の日の種類と時間帯のセルがなければ、推定しません。
3. `lastDay` が今日（日本時間）より 28 日以上前なら、推定しません。
4. そのセルが今日、実測との照合で止められていれば、推定しません。
5. 基準（`epoch` なら 0、`midnight` なら今日の日本時間 0 時）から、`経過 = (今 − 基準 − phase) mod cycle`、`次まで = cycle − 経過`。
6. 幅 `u = 2 × spread + 2000` ミリ秒。`次まで ≤ u` なら、その次の周期にします（`次まで += cycle`）。今が青かもしれないときも、次の周期の青の始まりを示すことになります。
7. 次の青の始まりの時刻が今と同じ時間帯に入らないなら、推定しません（時間帯の境目で周期が切り替わることがあるため）。
8. 表示する幅：下限 = `(次まで − u)` を 5 秒単位に切り下げ（0 未満なら 0）、上限 = `(次まで + u)` を 5 秒単位に切り上げ。

### 表示の規則

- 実測データの提供に協力していて、送信用トークンを取れるときだけ時刻表を取得します。アプリが前面にあり、前回の取得から 12 時間以上たっていれば取得し、端末のキャッシュに保存します。`ids` は付けず、すべての交差点の時刻表を取得します（どの交差点に関心があるかをサーバーに知らせないため）。7 日より古いキャッシュは使いません。
- 推定は、ツールバーの「推定」から開く画面にだけ出します。画面の冒頭には常に「推定は横断の判断に使えません。実際の信号と音響信号を必ず確かめてください。」と書きます。
- 文言は「次の青の始まり　およそ 40〜60 秒後（推定）」の形です。VoiceOver のラベルは「推定」で始めます。色（青・赤）の名前、信号の色を使った表示、読み上げの通知、振動、Live Activity、通知は使いません。
- 現在地（水平精度 30 m 以内、10 秒以内に得たもの）と交差点の位置（`timing_places` の種別 1）の両方が分かるときだけ推定を出します。交差点から 80 m 未満なら「交差点の近くでは推定を表示しません。信号を受信してください。」とだけ示します。
- その交差点の信号を直近 10 秒以内に受信していれば、推定を出さず「受信中の信号をご覧ください。」と示します。
- **実測との照合**：受信中に `Red → Green` の変化を受けたら、そのセルの推定で一番近い青の始まりと比べます。差が 5 秒を超えたら、そのセルの推定をその日（日本時間）のうちは止めます。
